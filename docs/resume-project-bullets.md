# 简历项目话术（AI 产品实习生方向）

> 目标：两个项目都按「背景 → 我做了什么 → 量化产出」组织，突出 **AI 产品设计闭环**，而不是"会调 API"。
> 分为「简历版」（精简 3~4 条，可直接粘贴）和「面试口述版」（展开 7 维度，用于面试深挖）。

---

## 项目一：媒体资产管理系统（AI 智能入库）

> 技术栈：Spring Boot + Spring Security + MyBatis-Plus + Redis + JWT + 智谱 GLM-4V

### 简历版

- **背景**：媒体素材入库需人工逐张填写标签与分类，效率低、标签不规范。
- **做法**：接入智谱 `glm-4v-flash` 视觉模型，实现「上传 → AI 识别 → 标签/分类自动回填（可人工修改）→ 确认入库」的智能入库链路；采用「受控分类字典 + few-shot」而非 RAG，把分类树清洗成模型可枚举清单，再用规则把模型输出映射回现有分类（匹配不上归"未分类"）。
- **工程**：图片压缩缩略图、`max_tokens` 受限、重复图缓存控制 Token 成本；AI 超时/失败自动降级为纯手动填写，不阻塞入库主流程。
- **运营**：用户改掉 AI 标签即落库一条 Bad Case（AI 原始输出 vs 用户最终值），以标签采纳率为北极星指标，支撑 prompt 持续迭代。

### 面试口述版（讲"为什么这么设计"）

1. **数据**：图片不是结构化数据，所以这里才需要模型"看图"；但分类是有限的——用「受控字典 + few-shot」逼模型输出落在已知集合，降低幻觉。
2. **模型**：`glm-4v-flash` 免费、国内直连、有视觉能力、快，符合"打标签"这种轻场景。
3. **评估**：离线用标注图集算准确率，上线看「采纳率」（用户有没有改 AI 的标签）。
4. **成本**：缩略图 + max_tokens + 重复图缓存。
5. **兜底**：模型失败降级手动填写，入库永远不阻塞。
6. **迭代闭环**：改标签 = Bad Case，落库复盘 → 调 prompt → 再观察采纳率。

## 项目二：智能快递柜系统（AI 客服 + 取件通知）

> 技术栈：SSM（Spring + SpringMVC + MyBatis）+ JSP + 智谱 GLM-4-Flash

### 简历版

- **背景**：取件用户反复问「到了吗 / 在哪 / 取件码」，人工客服重复劳动。
- **做法**：采用「确定性检索 + LLM 生成」而非 Agent——SQL 按手机号查快递作唯一事实源，模型只负责把查到的数据组织成话术，防幻觉靠"只基于给定数据回答，没有就说没有"；状态码转中文、时间格式化、手机号脱敏后再进模型。
- **工程**：上下文只注入最近快递、`max_tokens` 受限控制成本；模型失败/未配置 Key 自动降级为模板话术，客服链路不断。
- **运营**：每轮对话落库 `ai_chat_log`（脱敏 + 回答来源 + 转人工信号），以转人工率为北极星指标，形成「上线 → 埋点 → 复盘 → 调优」闭环；取件通知一键生成温馨文案。
- **附加**：顺带修复项目原有半成品——补齐登录鉴权、取件闭环、故障报修追踪、首页真实数据看板（剔除假数据）。

### 面试口述版（讲"为什么不用 Agent"）

1. **数据**：快递是结构化数据，SQL 按手机号查就是唯一事实源，不需要向量库/RAG。
2. **模型**：`glm-4-flash` 免费文本模型，简单问答/文案够用。
3. **评估**：转人工率 + 模型可用率（`answer_source=model` 占比），比空口说"效果好"更有产品感。
4. **成本**：上下文只给最近 N 条 + max_tokens + 规则先行（查数据走 SQL）。
5. **兜底**：未配置 Key / 超时 / 异常 → 模板话术，AI 永远不阻塞主流程。
6. **Bad Case**：转人工即信号，`ai_chat_log` 自动埋点零成本收集。
7. **为什么不用 Agent**：任务只有一个动作（查快递），SQL 一条语句就搞定；用 Agent 引入不确定性、增加 token 和延迟却零收益。
8. **规则 vs 模型**：有明确答案用规则（SQL），需要"理解+生成"才用模型。

## 一句话总括（写进简历"个人优势"或面试开场）

> 两个 Java 项目都不是"调一个 LLM 接口"的 AI 空壳——每个 AI 节点都有可讲的设计依据：数据怎么清洗、为什么选这个模型、成本怎么降、异常怎么兜底、Bad Case 怎么收集、为什么用规则+模型而不是 Agent、如何形成迭代闭环。
