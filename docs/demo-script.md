# 演示脚本 + 面试口述要点

> 目的：把「智能快递柜系统」从头到尾演示一遍，每一步都带一句可对面试官说的话。
> 配套数据：`src/main/resources/sql/demo-data.sql`（在 `database-init.sql` 之后执行）。

---

## 0. 准备工作

1. 数据库按顺序执行两个脚本（MySQL 客户端整文件跑）：
   - `src/main/resources/sql/database-init.sql`（建表 + 最小种子）
   - `src/main/resources/sql/demo-data.sql`（补演示数据）
2. 配置 `config/ai.properties` 填好真实智谱 Key。
3. IDEA + SmartTomcat 启动，浏览器打开 `http://localhost:8080/`。

演示账号：**admin / 123456**（管理员）、**test / 123456**（普通用户）、**wangxm / 123456** 等演示用户。

---

## 1. 登录与 RBAC（权限）

**演示动作**：用 `admin/123456` 登录 → 看左侧菜单全量；退出后用 `test/123456` 登录 → 对比菜单。

**要说的**：
> 这是我自己补上的鉴权层——登录 + 拦截器 + 角色区分。原项目是没有登录就能进后台的，我把它补成了"未登录跳登录页、按角色显示菜单"的完整链路。密码存的是 MD5，不是明文。

---

## 2. 快递柜 / 柜格管理

**演示动作**：新增一个快递柜 → 系统自动生成小/中/大柜格 → 点进去看柜格列表。

**要说的**：
> 创建快递柜时柜格是自动初始化的，不是手工一条条加的。这个"建柜即建格"的逻辑原项目是断的，我补上了。

---

## 3. 快递入库 → 取件（核心闭环）

**演示动作**：
1. 新增快递：填单号、寄件人、收件人手机号、选快递柜和柜格 → 状态「待取件」，对应柜格自动变「占用」。
2. 对某个待取件快递点「取件」→ 状态变「已取件」，柜格释放回「空闲」。

**要说的**：
> 这是系统最核心的业务闭环：入库占柜、取件释放。状态流转（待取件→已取件）和柜格状态是联动的，不是两张各写各的表。

---

## 4. 故障报修

**演示动作**：对某个快递柜点「报修」→ 填故障描述 → 状态「待维修」→「开始维修」→「完成维修」。

**要说的**：
> 报修是带状态机追踪的（待维修→维修中→已维修），原项目这里是个 stub（点了没反应），我把它做成了完整流程。

---

## 5. 首页数据看板

**演示动作**：登录后进首页，看快递总数、柜格占用数、待取件数。

**要说的**：
> 首页的数字是真实 SQL 统计出来的，不是写死的假数据。

## 6. AI 客服（重点演示，多留时间）

入口：首页导航「AI 客服」，或后台侧边栏「智能服务 → AI 智能客服」。

**核心演示**：输入手机号 `13812345678`（王小明）+ 问题「我的快递到了吗」→ 返回真实回答（他有 2 个待取件，分别在两个柜格）。

**四种效果都演示一遍，覆盖"规则 vs 模型 + 降级 + Bad Case"：**

| 场景 | 输入 | 预期 | 讲什么 |
|---|---|---|---|
| ① 正常命中 | 手机号 `13812345678` +「到了吗」 | AI 说"您有 2 个快递待取件，在 XX 柜格" | 数据是 SQL 查的，模型只负责组织话术 |
| ② 查无此人 | 手机号 `13000000000` +「到了吗」 | AI 说"没查到相关快递" | 没有就说没有，防幻觉 |
| ③ 转人工 | 手机号 `13612345678` +「转人工」 | 模板话术 + 落库 `is_transferred=1` | 转人工就是 Bad Case 信号 |
| ④ 模型降级 | 把 `ai.properties` 的 key 改错/删掉再问 | 返回模板话术，链路不断 | AI 挂了功能照常可用 |

**要说的（整段口述）**：
> 这个客服我用的是「确定性检索 + LLM 生成」，不是 Agent。快递是结构化数据，SQL 按手机号查就是唯一事实源，模型只负责把查到的数据说成人话，我明确告诉它"只基于给定数据回答，没有就说没有"，防止它编造。模型失败或者没配 Key，就降级成固定模板，客服永远不阻塞。每轮对话都会落一条 `ai_chat_log`，记录回答来源和是否转人工——转人工率就是我的北极星指标，用来复盘 Bad Case、迭代 prompt。

---

## 7. AI 取件通知

**演示动作**：后台「快递管理」列表，对某个「待取件」快递点「生成通知」→ 弹窗出温馨文案 → 复制。

**要说的**：
> 这是管理员侧的提效：一键生成取件通知文案，模型写出来人工可复制可改。文案生成是"需要理解+表达"的场景，所以用模型；查数据是"有明确答案"的场景，所以用规则。这是我判断"什么时候用规则、什么时候用模型"的例子。

---

## 8. 面试时最可能被追问的 3 个问题（提前准备）

**Q1：为什么不直接用 Agent / Function Calling？**
> 任务只有一个动作——按手机号查快递，一条 SQL 就搞定。用 Agent 要多轮往返、增加 token 和延迟，收益为零，还引入不确定性。查数据必须 100% 准确，我用 SQL 是确定的。

**Q2：你怎么证明 AI 有效果？**
> 用 `ai_chat_log` 埋点算两个指标：模型可用率（`answer_source=model` 占比，反映降级频率）和转人工率（`is_transferred=1` 占比，越低说明 AI 接得越好）。定期抽转人工的样本复盘，是数据问题就补数据、是 prompt 问题就调 prompt，再看转人工率是否下降。

**Q3：Token 成本怎么控制？**
> 只把查到的最近快递注入上下文、`max_tokens=512`、`temperature=0.3`、规则先行（查数据走 SQL 不走模型）。模型是"锦上添花"，规则是"保底承诺"。
