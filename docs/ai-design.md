# AI 智能客服与取件通知 —— 产品设计文档

> 本文档回答一个核心问题：**为什么这个 AI 功能要这么设计？** 每一条设计决策都有依据，可直接用于面试口述。
> 代码落点：`ai/ZhipuAiClient.java`、`service/impl/AiAssistantServiceImpl.java`、`controller/AiAssistantController.java`、`entity/AiChatLog.java`、`mapper/AiChatLogMapper.xml`、`ai_chat_log` 表。

---

## 一、背景与目标

**用户痛点**：取件用户会反复问三句话——「我的快递到了吗」「在哪个柜」「取件码多少」。这些问题的答案其实都存在数据库里（`t_package` 按手机号可查），如果全靠人工客服，是纯重复劳动。

**产品目标**：让用户输入手机号即可自助查询快递，后台一键生成取件通知文案，把重复问答从人工客服手里接过来。

**衡量指标（北极星）**：**转人工率**（用户问完 AI 还要转人工的比例）与 **问题解决率**（AI 直接解决的比例）。这两个指标直接反映"AI 有没有真的替代人工"。

---

## 二、数据：为什么这么清洗、切分

快递数据是**高度结构化**的（单号、收件人、柜机、柜格、状态、时间），和媒体系统里"从图片理解内容"完全不同。所以这里**不做 RAG、不做向量库**，而是：

1. **SQL 确定性检索**：`selectPackageDetailsByPhone(phone)` 按手机号直接查，查出来的就是唯一事实源。模型不负责"记数据"，只负责"组织话术"。
2. **状态码 → 中文**：`t_package.status` 是 `1/2/0`，SQL 里用 `CASE WHEN` 转成「待取件/已取件/已取消」，否则模型要自己猜数字含义，容易出错。
3. **时间格式化**：`put_in_time` 是 `DATETIME`，拼上下文前先 `SimpleDateFormat` 成 `yyyy-MM-dd HH:mm`，避免把一长串时间戳丢给模型。
4. **脱敏**：只给模型注入"该手机号"的快递，不喂无关手机号；日志落库时手机号 `maskPhone`（保留前 3 后 4，中间 `****`），防止客服日志泄露隐私。
5. **上下文裁剪**：只注入最近快递，避免一次灌入海量历史，控制 token 也控制回答聚焦。

> 一句话：**数据的"清洗"发生在进模型之前，用 SQL + Java 把结构化数据整理成模型可直接读的文字上下文。**

## 三、模型：为什么选 glm-4-flash

| 候选 | 结论 | 理由 |
|---|---|---|
| GPT / Claude | 不用 | 需付费 + 国内访问不稳定 |
| 本地小模型 | 不用 | 部署成本高，效果不稳定 |
| **智谱 GLM-4-Flash** | ✅ 选用 | **永久免费、国内直连、OpenAI 兼容、文本问答/文案够用** |

选型原则：这是一个**简单问答 + 文案生成**场景，不需要推理能力很强的旗舰模型，用最便宜的免费文本模型就能覆盖，剩下的靠规则兜底。模型名做成配置项 `ai.zhipu.model`，未来要升级直接改配置，不用改代码。

## 四、效果：怎么评估

AI 客服没法像分类那样算"准确率"，评估要落到**业务指标**和**可复盘样本**两个层面：

1. **线上指标**：`ai_chat_log` 表记录了每轮回答的 `answer_source`（`model` 模型生成 / `template` 模板降级）和 `is_transferred`（是否转人工）。据此能算出：
   - **模型可用率** = `answer_source=model` 的占比（反映降级频率）
   - **转人工率** = `is_transferred=1` 的占比（越低说明 AI 接得越好）
2. **Bad Case 复盘**：定期抽 `is_transferred=1` 或用户反复追问的记录，看模型哪里没答好，据此调 prompt。
3. **通知文案**：后台生成后人工可编辑，编辑即是一条"模型输出 vs 人工最终值"的对照样本。

> 关键点：**没有"测试集准确率"可吹时，就用真实的运营指标（转人工率、降级率）+ 可复盘日志来证明效果**，这比空口说"效果很好"更有产品感。

## 五、核心使用链路

### 客服对话（公开，无需登录）
```
用户输入手机号 + 问题
   → POST /assistant/chat
   → 1. SQL 按手机号查快递（规则）
   → 2. 拼成文字上下文
   → 3. 模型生成回答（模型）
   → 4. 失败则降级模板话术（规则兜底）
   → 5. 落库 ai_chat_log（脱敏）
   → 返回回答
```

### 取件通知（后台，需登录）
```
管理员在快递列表点「生成通知」
   → POST /assistant/notice/{id}
   → 查快递详情 → 拼上下文 → 模型生成温馨文案
   → 失败则降级固定模板 → 弹窗展示，可复制
```

交互设计要点：AI 客服是**"检索 + 生成"**，不是全自动写数据；通知是**"一键生成 + 可复制"**，人工始终保有最终确认权。

## 六、Token 成本：怎么降

| 手段 | 说明 |
|---|---|
| 上下文只给最近快递 | 不灌全量历史，输入 token 可控 |
| `max_tokens=512` | 限制输出长度，回答/文案用不了太多 |
| `temperature=0.3` | 低温度减少随机性，也更省重复生成的浪费 |
| 规则先行 | 查数据走 SQL，只有"组织话术"才走模型，模型调用量降到最低 |
| 失败即停 | 模型超时/异常不重试多次，直接降级，避免反复消耗 |

---

## 七、异常：怎么兜底

这是本功能最能体现工程严谨的地方——**AI 永远不阻塞主流程**：

1. **未配置 Key**：`ZhipuAiClient.isConfigured()` 检测 `api-key` 是否还是占位符 `your_zhipu_api_key`，是就直接走模板。
2. **模型超时 / 网络异常**：Hutool HTTP 设了 `timeout-ms=10000`，异常被 `try-catch` 吞掉 → `answer=null` → 走模板。
3. **模板兜底**：`buildTemplateAnswer` / `buildTemplateNotice` 用固定文案，保证用户**无论什么情况都能拿到一个有意义的回答**。
4. **日志失败不影响主流程**：`saveLog` 里 try-catch 包住，写日志失败也不影响给用户返回。

> 一句话：**模型是"锦上添花"，规则是"保底承诺"。模型挂了，功能照常可用，只是话术从"AI 生成"变成"固定模板"。**

---

## 八、Bad Case：怎么收集、怎么用

- **自动落库**：每轮对话都写进 `ai_chat_log`，记录 `answer_source` 和 `is_transferred`，零人工成本。
- **转人工即信号**：`isTransferRequest()` 检测问题里含「人工/投诉/客服/反馈」就标记 `is_transferred=1`，这些是天然的高价值 Bad Case 来源。
- **复用方式**：定期抽出 `is_transferred=1` 或降级样本 → 看是"查不到数据"（数据问题）还是"答非所问"（prompt 问题）→ 调 system prompt 或补模板分支 → 再观察转人工率是否下降。**这就形成了一个"上线 → 埋点 → 复盘 → 调优 → 再上线"的闭环。**

---

## 九、为什么用「普通流程」而不是 Agent

很多同学一上来就上 Agent / Function Calling，但这里**明确不用**，理由是：

1. **任务太简单**：只有"按手机号查快递"一个动作，一个 `selectPackageDetailsByPhone` 就解决了，不需要模型去"决定调用哪个工具"。
2. **确定性优先**：查数据必须 100% 准确，用 SQL 是确定的；让 Agent 动态决定调用，反而引入不确定性。
3. **成本与延迟**：Agent 要多次往返调用，token 和耗时都更高，收益却为零。

**架构定位：确定性检索（规则）+ LLM 生成（模型）**。模型只负责"把查到的数据说成人话"，不负责"去查数据"。

---

## 十、什么时候规则兜底、什么时候用模型

| 场景 | 方案 | 原因 |
|---|---|---|
| 查快递、判状态 | **规则（SQL）** | 有明确答案，必须 100% 准确，规则最稳 |
| 组织回答话术 | **模型** | 需要理解问题、灵活组织语言，规则写死很僵硬 |
| 取件通知文案 | **模型** | 需要"温馨、人性化"的表达，模板太机械 |
| 模型失败 / 未配置 | **规则（模板）** | 兜底，保证链路不断 |

判断标准一句话：**有明确答案的用规则，需要"理解 + 生成"的才用模型。**

---

## 十一、节点失败后如何继续

整条链路是**可降级的串行结构**，每一环失败都有下一步兜底：

```
SQL 检索失败 → 上下文为空 → 模型回答"没有找到相关快递"（仍是有效回答）
模型调用失败 → answer=null → 降级模板话术（链路不断）
模板也异常   → controller try-catch → 返回固定兜底文案
日志写入失败 → 吞掉异常，不影响主返回
```

没有任何一个节点失败会导致整个客服功能不可用——这正是"异常兜底"在产品层的意义：**用户永远能拿到一个回答。**

---

## 十二、产品迭代闭环（总结）

1. **上线前**：定义转人工率 / 模型可用率两个指标，明确"北极星 = 转人工率下降"。
2. **上线后**：`ai_chat_log` 自动埋点，持续积累真实问答样本。
3. **复盘**：定期抽转人工 / 降级样本，定位是数据问题还是 prompt 问题。
4. **调优**：改 prompt 或补模板分支，再观察指标变化。
5. **模型升级**：需要更强能力时，只改配置项 `ai.zhipu.model`，代码零改动。

> 这套"指标 → 埋点 → 复盘 → 调优"的闭环，就是 AI 产品经理区别于"只会调 API 的开发者"的核心竞争力。
